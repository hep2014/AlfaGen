# Логирование и диагностика

## Включение

Перед запуском команды из README:

```powershell
$env:AUDIT_LOG_DIR = 'logs'
```

JSON-события пишутся в stderr и `logs/audit.jsonl`; ротация — 5 МБ на файл,
до трёх архивных файлов плюс текущий. Каталог исключён из Git.
Без переменной остаётся только консоль. В пилоте права на каталог, срок хранения
и централизованный сбор настраивает эксплуатация; ротация не заменяет политику хранения.

## Что записывается

Каждый HTTP-запрос получает случайный серверный `request_id`, который возвращается
в заголовке `X-Request-ID`. Значение от клиента не используется: оно может содержать ПД.
Параллельные запросы имеют независимый контекст, включая обработчики в пуле потоков.

События: `request_started`, `authorization`, `validation`, `stage_started`,
`stage_finished`, `detection`, `operation_finished`, `request_finished`, `request_failed`.
Этапы: detection, tokenization, vault_write, provider, output_guard, restoration.
При ошибке этап может остаться без `stage_finished`; код ответа и завершение операции
позволяют найти сбой по последнему начатому этапу. Успех этапа не означает успех запроса.

Поля ограничены: время UTC, request_id, фиксированное имя операции/этапа,
статус, HTTP-код, длительность, версия политики, количества обнаруженных типов.
Нет свободного поля для содержимого запроса, ключей, session_id, соответствий или трассировки исключения.
Сырые URL, query string, заголовки и произвольные имена систем в аудит не попадают.
Версии политики и названия этапов — доверенная административная конфигурация, не текст пользователя.

Пример формы события (значения иллюстративные):

```json
{"timestamp":"2026-09-22T10:00:00+00:00","event":"request_finished","request_id":"d950936fd23e4b4693bbf2853c5f6ee3e","operation":"mask","status_code":200,"elapsed_ms":1.5}
```

У Uvicorn отключаем access log, потому что стандартная запись может содержать query string.
Настройка `configure_logging` также отключает logger `uvicorn.access`.
Будущие HTTP-клиенты и reverse proxy требуют такой же настройки: защита наших событий
не гарантирует, что произвольный сторонний debug-лог не сохранит содержимое.

## Метрики

- `privacy_http_requests_total{operation,status_code}` — HTTP-результаты, включая 401/403/404/413/422.
- `privacy_http_seconds{operation}` — время запроса, включая чтение тела, валидацию и локального провайдера.
- `privacy_requests_total{operation,status}` — операции обработки после авторизации/валидации.
- `privacy_operation_seconds{operation}` — их время; для roundtrip включает локальный провайдер.
- `privacy_entities_total{kind}` — количества найденных сущностей.

RPS маскирования: `sum(rate(privacy_http_requests_total{operation="mask"}[1m]))`.
Не включать health/metrics в бизнес-RPS. Не использовать request_id как label метрики.
TPS пока не реализован: нужен выбор токенизатора и точное определение входящих/исходящих токенов.

## Проверки

Тесты проверяют JSON-корреляцию событий, изоляцию восьми параллельных запросов,
отсутствие контрольного ПД/ключа в аудите и ошибках, отказы провайдера, 413 до JSON-разбора,
неизвестные и повреждённые токены, новые ПД в ответе модели.
Это проверки конкретных путей, не доказательство отсутствия всех возможных утечек.
